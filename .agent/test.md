### 4. `test.md`：测试计划与实际结果

**核心目标：提供能够证明功能正确性的真实证据。**

每项需求必须具有独立的测试文档，由 Agent 生成、执行和维护。

#### 测试计划

每个测试用例应包含：

- 测试编号。
- 对应的 Spec 验收条件。
- 测试目标。
- 前置条件。
- 测试输入与操作步骤。
- 预期结果。
- 测试方式。
- 对应测试代码位置（如适用）。

测试应覆盖：

- 正常场景。
- 边界场景。
- 异常场景。
- 与本次修改有关的旧功能回归场景。

#### 测试执行记录

实际执行后必须记录：

- 测试执行命令或操作步骤。
- 实际执行结果。
- 通过、失败或未执行状态。
- 关键输出、错误信息或日志位置。
- 失败原因与修复情况。
- 修复后的重新测试结果。

自动化测试应保留可复现的执行方式。

对于无法合理自动化的 UI、动画、键盘操作或外部通信测试，应记录明确的手动验证步骤。

未实际执行的测试不得标记为通过。

#### 测试状态

- `PASS`：已执行，实际结果满足预期。
- `FAIL`：已执行，实际结果不满足预期。
- `BLOCKED`：受环境或依赖限制，无法完成验证。
- `NOT RUN`：尚未执行。

不得将代码检查、静态分析或编译成功直接等同于功能测试通过。

如果仅完成了部分验证，必须明确说明已验证范围和未验证范围。

#### 测试失败处理

1. 分析失败原因。
2. 判断问题属于实现缺陷、测试缺陷还是环境问题。
3. 实现缺陷应修复代码并重新测试。
4. 只有测试本身确实存在缺陷时才允许修改测试，并记录原因。
5. 不得通过删除测试或无依据地放宽断言使测试通过。
6. 修复后必须重新执行受影响的测试。

#### 完成标准

测试文档必须能够回答：

- 测试了哪些功能？
- 每项测试的预期结果是什么？
- 实际执行结果是什么？
- 有什么证据证明结果？
- 哪些测试失败或未执行？
- 是否存在尚未解决的问题？
