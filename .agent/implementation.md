### 5. `implementation.md`：实际实现与复盘说明

**核心目标：让用户仅通过文档，就能理解本次需求实际完成了什么、修改了什么、如何实现以及存在什么问题。**

该文档应在实现过程中根据实际情况维护，并在完成测试后整理为最终版本。

#### 必须包含的内容

**1. 实现概述**

- 本次实际完成的功能。
- 与 Spec 对应的实现情况。
- 未完成或部分完成的功能。
- 最终用户能够观察到的效果。

**2. 修改范围**

列出本次主要修改或新增的：

- 文件。
- 类。
- 模块。
- 接口。
- 数据结构。
- 配置项。

说明每项修改的作用。

不要求机械列出无关文件，但必须覆盖理解本次实现所需的关键改动。

**3. 实现逻辑**

按照实际执行流程说明：

- 功能从哪里触发。
- 请求或事件如何传递。
- 哪些模块负责处理。
- 关键数据如何流动。
- 最终结果如何产生和展示。

重点解释关键实现逻辑与技术决策，不重复描述简单代码。

**4. 源码逻辑树**

必须根据真实源码生成本次需求的调用关系树。

要求：

- 使用中文描述业务行为。
- 结合实际类名、方法名说明调用关系。
- 展示关键入口、处理过程和结果。
- 只覆盖本次需求涉及的主要逻辑。
- 不确定的调用关系必须标记为待确认。
- 不得根据设计方案猜测实际调用关系。

逻辑树格式示例：

```text
用户触发功能
└─ MainForm：接收用户操作
   └─ Controller.HandleAction()：处理操作
      ├─ Validator.Validate()：验证输入
      ├─ Service.Execute()：执行核心逻辑
      │  └─ Repository.Save()：保存处理结果
      └─ MainForm.UpdateView()：更新界面
```

以上仅为格式示例，实际文档必须以当前源码为准。

**5. 关键技术决策**

记录影响实现结果的重要决策：

- 遇到了什么问题。
- 为什么选择当前方案。
- 是否考虑过其他方案。
- 当前方案存在什么限制。

不要求记录每一个普通编码决定。

**6. 旧功能影响**

明确说明：

- 本次修改可能影响哪些旧功能。
- 哪些旧功能已经验证。
- 使用了什么方式验证。
- 哪些影响尚未确认。

不得在缺少依据时直接宣称“对旧功能无影响”。

**7. 测试与验证总结**

- 自动化测试执行情况。
- 手动测试执行情况。
- 回归测试结果。
- 失败或未执行的测试。
- 对应 `test.md` 的详细记录位置。

**8. 遗留问题与后续建议**

- 尚未解决的问题。
- 已知限制。
- 未验证的风险。
- 后续可优化的方向。

没有遗留问题时应明确说明，但不得隐瞒已发现的问题。

#### 完成标准

用户仅阅读 `implementation.md`，应能够回答：

1. 这次实现了什么功能？
2. 哪些文件和模块发生了变化？
3. 功能内部是如何执行的？
4. 为什么采用当前实现方案？
5. 对已有功能产生了什么影响？
6. 测试结果如何，证据在哪里？
7. 是否还有未解决的问题？
