### 2. `spec.md`：需求规格与验收标准

**核心目标：让用户在开发前理解并确认最终功能效果。**

每项需求必须具有独立的 `spec.md`。

#### 必须包含的内容

**1. 需求目标与范围**

- 本次需要解决什么问题。
- 最终需要实现哪些功能。
- 本次明确不包含哪些功能。

**2. 最终功能表现**

从用户视角说明功能完成后的实际效果：

- 用户能够看到什么。
- 用户能够执行什么操作。
- 系统收到操作后会发生什么。
- 最终结果如何展示。
- 与原有功能相比发生了哪些变化。

不得仅用技术实现描述代替最终功能说明。

**3. 页面效果与交互流程**

涉及界面时，应明确：

- 页面布局和主要显示区域。
- 新增或修改的按钮、控件及其用途。
- 鼠标、键盘等交互方式。
- 用户操作后的界面反馈。
- 正常、边界和异常情况下的表现。

当文字难以清晰表达页面效果时，优先提供可直接在浏览器打开的 HTML 原型。

简单需求可以只使用文字说明，不强制生成原型。

原型用于确认预期效果，不代表实际功能必须采用 HTML 实现。

**4. 技术要求与项目约束**

结合现有源码说明：

- 涉及的主要模块。
- 已确定的技术要求。
- 必须遵守的项目约束。
- 需要保持兼容的已有功能。

具体业务参数、算法要求和技术约束应在对应需求中定义，不写入 AGENTS。

**5. 验收条件**

每条验收条件必须：

- 可以明确判断通过或失败。
- 能够对应具体的功能行为。
- 说明预期结果。
- 覆盖重要的正常、边界和异常场景。

不得使用“功能正常”“运行良好”等无法独立判断的表述作为唯一验收依据。

**6. 风险与未决问题**

- 说明已识别的技术风险。
- 列出影响需求范围或最终效果的未决问题。
- 对能够通过阅读源码确定的问题，Agent 应优先自行分析。
- 对无法确定的重要需求问题，必须请求用户确认。

**7. 学习目标（按需）**

记录本需求涉及的知识点，供后续解释和复盘使用。

学习目标不能代替功能验收条件。

#### 完成标准

只有满足以下条件，Spec 才能提交用户确认：

- 最终功能表现已经清楚描述。
- 重要交互规则已经明确。
- 验收条件可以实际执行。
- 已有功能的兼容要求已经识别。
- 不存在会影响实现方向的重大未决问题，或已明确列出等待用户决策。

**用户明确确认 Spec 后，才能进入后续规划与评审阶段。**
