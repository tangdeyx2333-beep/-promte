# Git 提交规范

本文约定本项目的分支命名、提交信息和提交内容，便于回顾每项需求的实现与验证。

## 分支命名

每项需求从最新的 `master` 创建独立分支。分支名采用：

```text
<类型>/<编号>-<简短名称>
```

分支前缀按工作类型区分：`feat/`（功能开发）、`fix/`（Bug 修复）、`doc/`（文档修改）。编号对应需求编号；不属于 10 个阶段路线图的文档或维护事项使用 `00`。名称使用简短英文小写词组，以连字符分隔。

示例：

```text
feat/01-grid-rendering
doc/00-git-commit-guidelines
fix/03-pathfinding-boundary-fix
```

开始工作前先检查工作区状态，保留已有改动；不要把不同需求叠加到同一需求分支。若本地没有 `master`，先检查远程分支并同步；不得未经确认改从其他分支创建。

## 工作区与提交历史管理

- **单工作区开发**：统一在当前工作区开发，不使用 Git Worktree 创建额外工作区。
- **需求分支隔离**：一个需求对应一个独立分支，不混入其他需求的改动；切换分支前检查并妥善处理未提交修改。
- **开发过程提交**：允许在需求分支上多次提交，便于阶段性保存、验证和回退。
- **合并提交整理**：需求完成并验证后，使用 Squash Merge 合并到 `master`，使一个需求在 `master` 中只对应一个 Commit；合并提交信息遵循本文规范。
- **保持历史整洁**：避免将零散的开发、修复、测试和文档调整提交直接合并进 `master`，不产生额外的合并提交。
- **安全约束**：不得擅自丢弃已有工作区改动，不得对共享分支强制推送或重写历史。

## 提交信息

提交信息使用中文，建议格式：

```text
<类型>(<范围>): <中文摘要>
```

摘要应简洁说明本次提交做了什么，使用动词开头，不加句号。类型使用 `feat`（新功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）或 `chore`（维护）。范围可写模块或需求编号；不适用时可省略括号范围。

示例：

```text
feat(01): 添加网格视图平移与缩放
fix(pathfinding): 修复起点等于终点时的路径结果
docs: 补充中文 Git 提交规范
```

一个提交尽量只表达一个清晰、完整的变更。需要补充背景或验证结果时，在提交正文中用中文说明。

## 提交内容

- 只提交本项目的代码、测试代码和项目文档，以及运行这些内容所必需的项目配置文件。
- 只暂存当前需求相关且经过检查的文件；提交前用 `git diff --cached` 检查暂存内容。
- 不提交编译产物、缓存、临时文件、运行日志、测试结果、IDE 用户配置或其他机器生成文件。
- 常见排除项包括 `bin/`、`obj/`、`artifacts/`、`.vs/`、`TestResults/`、`*.user`、`*.cache`、`*.log` 和临时文件。新增生成文件类型时，应同步评估是否需要加入 `.gitignore`。
- 如果代码或文档变更意外包含上述生成文件，先从本次暂存区移除，再提交；不要为使提交通过而删除其他人的工作区改动。
