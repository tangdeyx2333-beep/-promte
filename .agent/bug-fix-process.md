# Bug 修复流程规范

修复 Bug 时，按以下步骤执行。每项需求维护一份独立的 Bug 修复记录。

1. **明确复现方法**  
   修改代码前，确定稳定复现 Bug 的操作步骤、前置条件和实际表现。若无法稳定复现，应记录已观察到的现象及复现限制，不要猜测原因。

2. **查找根本原因**  
   根据源码、运行行为和必要的诊断信息定位原因，并区分已确认的事实与待验证的判断。

3. **明确修改方案**  
   说明计划如何修复，以及可能受影响的行为。若方案会改变现有需求或功能约定，应先修订并确认相关需求。

4. **仅修改 Bug 所需内容**  
   改动前需要用户确认bug修复方案通过
   改动限于修复该 Bug 所必需的代码和测试，不顺带调整无关逻辑。不得通过删除或无依据地放宽测试来使其通过。

5. **执行回归验证**  
   对可能受影响的旧功能运行相关回归测试。若无法自动化验证，应说明原因并提供手动验证方法。

6. **记录修复结果**  
   每项需求在其目录下维护一份 `bug-fix.md`，汇总该需求涉及的所有 Bug。每个 Bug 按以下结构单独记录，并追加到文档末尾：

## `bug-fix.md`：Bug 修复记录

每个 Bug 的记录应包含：

1. **Bug 描述**：说明问题现象及其影响。
2. **稳定复现方法**：列出复现所需的前置条件和操作步骤。
3. **根本原因**：说明问题产生的原因；尚未确认的判断应标为待验证。
4. **修改方案**：说明针对该原因采取的修复方式和可能影响的范围.
5. **结果**：记录实际修改内容及修复后的表现。
6. **回归验证**：列出可能受影响的旧功能及测试结果。测试通过时记录为通过；没有适用的回归测试时，说明检查依据，并明确指出“本次修改无额外影响”。如果影响尚未验证，应如实记录为待验证。
7. **为什么解决**: 需要输出核心的解决代码，并且解释之前如何加上这段代码修改了什么逻辑，最终解决了这个问题。
